STAFF DAILY BOOKING INTEGRATION HANDOFF

给组员的中文摘要
本次只改 Staff 和本地测试。下面的字段约定尚未部署到正式 Firebase。
Customer：选日期后按 tableReservations/{yyyy-MM-dd}/{tableKey} 判断占用；
同时检查 isEnabled 和 capacity。改变日期/人数后清除已选餐桌。
订单 tableId 存 Firebase 节点 key，bookingDate 存 yyyy-MM-dd，guestCount 存数字。
创建 PENDING 订单与占用名额必须原子完成，并由服务端规则拒绝重复占用。
不要读取其他顾客的完整订单来判断可订性。
Manager：建桌时初始化 isEnabled 和 occupancyStatus，之后只更新必要字段，
不能用旧实体整条覆盖，否则会丢失新字段。现有 status 不再是 Staff 的权威字段。
规则负责人：合并各角色权限和跨节点一致性校验，不能直接部署这里的 Staff-only 测试规则。
迁移负责人：先备份、协调暂停旧版本写入，再转换日期、桌号 key 和人数；
补建 PENDING/ACCEPTED/PREPARING/READY/COMPLETED 的预约索引；
同桌同日重复订单、重复桌号、旧 RESERVED 含义不明的记录需要人工确认。
全部配合完成前，Staff 的旧格式餐桌只读，缺失/不匹配预约名额的订单禁止状态修改。
Staff 的 Release table 只改现场占用；Disable bookings 不删除既有预约；
Reject/Cancel 释放日期名额，Complete 仍保留当日名额。

Scope: Staff Java files and emulator tests only. No Customer, Manager, shared model,
production rules or production data were changed. This is NOT ready for mixed-version
production deployment until the team completes the coordination below.

Contract
1. tables/{tableKey}: tableNumber (display only), capacity (number),
   isEnabled (boolean), occupancyStatus (AVAILABLE/OCCUPIED), updatedAt (server timestamp).
2. Orders/{orderId}: tableId = database tableKey, bookingDate = yyyy-MM-dd
   in Pacific/Auckland, guestCount = positive number. Keep existing order fields.
3. tableReservations/{yyyy-MM-dd}/{tableKey}/orderId = owning order ID.
   PENDING/ACCEPTED/PREPARING/READY/COMPLETED hold the day.
   REJECTED/CANCELLED release it. COMPLETED never releases it.

Customer work
- Pass the selected local date and guest count to the table selector.
- Read tables and that day's reservation index; disable stopped/full/booked tables.
- Reset table selection when date or guest count changes.
- Store real table keys, canonical dates and numeric guest counts.
- Create a PENDING order and claim its slot atomically, with server-side uniqueness
  enforcement. Checking first and then unconditionally writing is NOT sufficient.
- Do not read other customers' full orders to show availability.
- If Customer cancellation is implemented, agree its permitted status transitions
  and release only its own slot in the same atomic operation.

Manager / data-owner coordination
- Initialize the new table fields when creating tables. Update fields individually;
  do not overwrite a whole table using the old shared model, which drops new fields.
- Update stop/enable controls to isEnabled. On-site operations use occupancyStatus.
- Shared Order remains unchanged; Customer's reader must handle numeric guestCount.
  Staff parses strings/numbers itself to avoid breaking other roles.

Migration (backup first; no automatic migration in this change)
- Convert old date strings strictly, map table numbers to unique database keys,
  and convert guest counts. Ambiguous/missing/duplicate table numbers need review.
- Initialize isEnabled and occupancyStatus; legacy RESERVED must be reviewed,
  since it cannot reliably tell us current physical occupancy.
- Build the index for every non-rejected/non-cancelled order, including PENDING
  and COMPLETED. Resolve duplicate same-day/table orders manually before indexing.
- Coordinate a write freeze / version rollout so old clients cannot create bookings
  without an index. Staff shows unmigrated tables read-only and refuses order state
  changes if canonical date, table key or matching slot is absent.
- Staff does not mirror new states into legacy status: one old field cannot represent
  booking enabledness and physical occupancy independently.

Firebase rules owner
- tools/staff-emulator/database.rules.json is a STAFF-ONLY emulator fixture.
  Do NOT replace production rules with it: Customer and Manager writes are absent.
- Merge and review the invariant checks with all role policies. No root read/write grant.
- Reject order-only cancellation and slot-only deletion; validate final multi-path state.
- Refuse deletion of another order's slot, and reject invalid order state transitions.
- Keep immutable booking fields and order meal contents protected after creation.
  Staff completion checks served items before writing; production must also enforce
  the team's meal-completion policy (trusted backend if needed).
- Inspect overlapping parent grants: broad allow rules bypass deeper write restrictions.
- Test Customer simultaneous booking, Customer/Staff cancel races, unrelated-date
  isolation, permission denial and migration before deploying.

Staff behavior
- Accept keeps the slot; Reject/Cancel atomically write Orders status/updatedAt and
  remove the slot, subject to server rules. Failed writes report no saved changes.
- Complete keeps the slot. Release table changes physical occupancy only.
- Disable bookings keeps all orders and date slots; existing bookings require explicit
  cancellation. A disabled table can still be marked occupied/released for existing guests.
- Table cards list date/status for day-holding orders, including completed bookings.

Reference: https://firebase.google.com/docs/database/web/read-and-write
Multi-location updates are atomic; conflict rejection requires matching security rules.

双方具体交换的数据（示例，不是线上数据）
不是 Customer 直接调用 Staff Activity，也不是 Staff 返回 HTTP response。
双方通过 Firebase 交换数据：Customer 创建订单和日期名额，Staff 监听后处理，
Customer 再监听自己订单的状态变化。大小写和路径必须一致。

前提：Manager/迁移负责人已创建 tables/tableKey123：
{
  "tableNumber": "T1",
  "capacity": 4,
  "isEnabled": true,
  "occupancyStatus": "AVAILABLE"
}
Customer 选桌时读取这个节点和 tableReservations/2026-10-24，
但不要替 Staff 修改餐桌的启用/现场状态。

Customer 创建预约的多路径更新示例：
{
  "Orders/orderKey456": {
    "orderId": "orderKey456",
    "customerId": "CUSTOMER_AUTH_UID",
    "tableId": "tableKey123",
    "bookingDate": "2026-10-24",
    "guestCount": 2,
    "status": "PENDING",
    "createdAt": {".sv": "timestamp"},
    "updatedAt": {".sv": "timestamp"}
  },
  "tableReservations/2026-10-24/tableKey123": {
    "orderId": "orderKey456"
  },
  "OrderItems/orderKey456/itemKey789": {
    "menuItemId": "menuKey789",
    "mealName": "Grilled salmon",
    "price": "24.00"
  }
}
上面是 updateChildren 的相对路径映射，绝不能用 setValue 覆盖数据库根节点。
OrderItems 继续使用现有菜单快照字段，imageUrl 可选；没有餐品时无需写示例餐品。
所有写入需成功后才提示预约成功。Firebase 规则必须禁止覆盖已被占用的日期名额；
单靠 updateChildren 的原子性并不能防止两个 Customer 抢同一张桌。

Staff 处理后，Customer 应观察的结果：
- 接单：Orders/orderKey456/status = ACCEPTED；日期名额保留。
- 拒绝：status = REJECTED；同一原子更新删除对应日期名额。
- 取消已接订单：status = CANCELLED；同一原子更新删除对应日期名额。
- 完成：status = COMPLETED；日期名额保留，当天仍不能再订。
- 上述状态更新还会写 Orders/orderKey456/updatedAt 服务端时间戳。
- 上菜：Orders/orderKey456/servedItems/itemKey789 = true。
- 停用预约：tables/tableKey123/isEnabled = false，既有订单/名额不变。
- 现场占用/释放：occupancyStatus = OCCUPIED / AVAILABLE，日期名额不变。
Staff 不额外创建 response 节点；失败只向 Staff 操作者显示错误，不伪造 Customer 状态。
Customer 只能读取自己的订单及必要的名额/餐桌数据，不能因此开放其他顾客资料。
